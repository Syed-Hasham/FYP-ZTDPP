ZTDPP Frontend and Cryptographic Signer / HSM Simulator Explanation
===================================================================

This document explains how the Zero Trust Digital Provenance Platform (ZTDPP) frontend and cryptographic signer/HSM simulator work together, what each file does, and how they are linked.

The explanation focuses on:
- The React frontend app and UI components
- The frontend API integration with the backend
- The cryptographic signer and simulated hardware security module (HSM)
- The backend verification pipeline and how it uses signer output
- All relevant files involved in these flows

---

1. OVERVIEW
-----------

ZTDPP is a multi-component system built around a trust score for images. The frontend provides a user-facing web UI for:
- signing images with a simulated HSM
- uploading signed or unsigned images for verification
- displaying verdicts and a detailed breakdown of cryptographic and AI analysis

The backend provides the actual verification and signing endpoints. The signer utility generates cryptographic metadata and embeds it into images.

### 2.1 `frontend/src/App.jsx`

`App.jsx` is the main React component.
It defines global UI state and switches between two modes:
- `verification`: image provenance verification flow
- `signer`: HSM signing simulator flow

Key state variables:
- `isDark`: theme toggle for dark/light mode
- `appMode`: either `'verification'` or `'signer'`
- `phase`: current UI step in verification (`upload`, `loading`, `results`, `error`)
- `selectedFile`: currently chosen file object
- `previewUrl`: object URL for the selected image preview
- `result`: backend verification response object
- `errorMsg`: any error message returned from the backend

Core functions:
- `handleFileSelect(file, url)`: stores selected file + preview URL
- `handleAnalyze()`: calls `verifyImage(selectedFile)` and updates UI state
- `handleReset()`: clears file, preview, result, and error state

UI structure:
- Header and tabs that switch between verification mode and signer mode
- In verification mode:
  - `ImageUploader` for file selection
  - `InfoCard` for backend health
  - a button to analyze the selected image
  - result view with image preview, trust score, verdict, and breakdown
- In signer mode: `SignerPage` renders the signing workflow

`App.jsx` imports and uses the API function `verifyImage` from `frontend/src/api/api.js`.
It also imports all UI components for modular display.

### 2.2 `frontend/src/api/api.js`

This module contains the HTTP client used by the frontend.
It defines:
- `BASE_URL = 'http://localhost:8000'`
- `verifyImage(file)`: POSTs the image to `/verify`
- `checkHealth()`: GETs `/health`
- `signImage(file, deviceId)`: POSTs the image and device ID to `/sign`

Error handling:
- It reads backend JSON error responses and converts them into readable `Error` objects.
- This allows UI components to show meaningful failure messages.

### 2.3 `frontend/src/components/Header.jsx`

`Header.jsx` renders the top navigation and information panel.

### 2.4 `frontend/src/components/ImageUploader.jsx`

- validation for file type (`image/jpeg`, `image/png`)

The component emits the selected file and preview URL to `App.jsx`.

### 2.5 `frontend/src/components/InfoCard.jsx`

It presents:

### 2.6 `frontend/src/components/TrustScorePanel.jsx`

This component displays the overall trust score.
It renders a circular progress ring and a `VerdictBadge`.
The trust score is shown as a percentage, and the ring color changes based on verdict.

### 2.7 `frontend/src/components/VerdictBadge.jsx`

This simple component maps verdict values to styled badges.
Supported verdicts:

Each badge uses a different icon and color.

### 2.8 `frontend/src/components/BreakdownSection.jsx`

This component shows the detailed verification breakdown:

It uses expand/collapse UI sections and status icons.
For AI analysis, it renders a progress bar showing the real/synthetic probability split.

### 2.9 `frontend/src/components/SignerPage.jsx`

This is the HSM simulator UI.
It allows the user to:
- choose an image file

It calls `signImage(file, deviceId)` from `frontend/src/api/api.js`.
On success, it downloads a signed image blob to the user’s machine.

3. BACKEND AND FRONTEND LINKAGE
------------------------------

The frontend communicates with the backend using two main endpoints:
- `/verify` — verification pipeline
- `/sign` — image signing simulator

Additional backend endpoints:
- `/health` — health check
- `/register-device` — register a camera device public key

The frontend is configured to call the backend at `http://localhost:8000`,
and the backend permits CORS from `http://localhost:5173`, which is the default Vite development port.

The signing UI uses the same backend as the verification UI, enabling end-to-end flow:
1. Use `SignerPage` to sign an image via `/sign`
2. Upload the signed image in verification mode
3. The backend validates the signature and AI score
4. The frontend displays the combined trust verdict

4. BACKEND VERIFICATION PIPELINE
--------------------------------

Main backend file: `backend/main.py`

Supporting backend modules:
- `backend/crypto_verifier.py`
- `backend/ai_inferencer.py`
- `backend/aggregator.py`
- `backend/registry.py`
- `backend/schemas.py`
- `backend/registry/schema.sql`

### 4.1 `backend/main.py`

`backend/main.py` is a FastAPI application that exposes all backend endpoints.
Its responsibilities include:
- startup database initialization via `init_db()`
- input validation for uploaded files
- temporary file management
- concurrent execution of AI and crypto checks
- computing final trust score
- returning structured JSON responses
- invoking the signer utility for `/sign`

Endpoints:
- `GET /health`
  - returns `{status: 'ok'}`
- `POST /register-device`
  - accepts `device_id` and `public_key_pem`
  - stores the device in SQLite
- `POST /verify`
  - accepts a file upload
  - saves the file temporarily
  - validates file type and size
  - calls `crypto_verify` and `ai_predict` in parallel
  - if both return, computes trust score via `compute_trust`
  - returns a `VerifyResponse`
- `POST /sign`
  - accepts a file upload and a `device_id` form field
  - saves the file temporarily
  - invokes `signer/signer.py` as a subprocess
  - returns the signed image file

Concurrency:
- `/verify` uses `asyncio.get_running_loop().run_in_executor(None, ...)`
  because `crypto_verify` and `ai_predict` are synchronous CPU-bound functions.

Temporary files:
- both `/verify` and `/sign` save the uploaded file in the OS temp directory
- `/verify` deletes the temp file after processing
- `/sign` preserves the output long enough for `FileResponse` to send it

### 4.2 `backend/schemas.py`

Defines Pydantic models used by FastAPI.
Models:
- `CryptoResult`
- `AIResult`
- `VerifyResponse`
- `DeviceRegistration`

These models shape the JSON returned by `/verify` and the JSON accepted by `/register-device`.

### 4.3 `backend/registry.py`

This module manages the trusted device registry on disk.
It stores:
- `device_id`
- `public_key`
- `registered_at`
- `trusted` flag

Functions:
- `init_db()` reads `backend/registry/schema.sql` and creates the database.
- `register_device(device_id, public_key_pem)` inserts or replaces the device.
- `get_public_key(device_id)` returns the PEM public key if the device is trusted.

This is the backend link between the signature embedded by the signer and the verification routine.

### 4.4 `backend/registry/schema.sql`

SQL schema for the device registry.
It creates the `devices` table and also includes a seeded entry for `CAM-001`.
The seed includes a public key so the demo can verify signed images from that device immediately.

### 4.5 `backend/crypto_verifier.py`

This module verifies the cryptographic manifest embedded in an image.
Its steps are:
1. parse the manifest from the image
   - JPEG: EXIF `UserComment` field
   - PNG: `tEXt` chunk with key `ZTDPP_Manifest`
2. extract `device_id`, `sha256_hash`, and `signature`
3. compute SHA-256 of the raw RGB pixel bytes
4. compare the computed hash to the manifest hash
5. retrieve the device public key from the registry
6. verify the ECDSA P-256 signature over the same raw pixel bytes

The module returns a `CryptoResult` with:
- `valid`: whether the full cryptographic check passed
- `hash_match`: whether the digest matched
- `sig_valid`: whether signature verification succeeded
- `device_id`: the originating device ID

Important details:
- It uses `PIL.Image.convert('RGB').tobytes()` to ensure deterministic pixel bytes
- It reads JPEG EXIF safely and handles PNG metadata separately
- If the device is not in the registry, the signature is treated as invalid

### 4.6 `backend/ai_inferencer.py`

This module loads the trained EfficientNet-B4 model from `checkpoints/best_model.pth`.
It performs:
- image load and resize to `224×224`
- RGB conversion
- `numpy` normalization using ImageNet mean/std
- model inference
- temperature scaling and probability clamping

It returns an `AIResult` with:
- `probability_real`: a float between 0.05 and 0.95
- `artifacts_detected`: boolean true if the AI judges the image likely fake

Important detail:
- The model output is clamped so the AI never produces an absolute `0.0` or `1.0` score.
- This prevents the AI alone from fully overriding cryptographic evidence.

### 4.7 `backend/aggregator.py`

This module computes the final trust score:
- `trust_score = alpha * crypto_score + (1-alpha) * ai_score`
- `crypto_score = 1.0` if cryptographic verification passed, else `0.0`
- `ai_score = probability_real`

With `alpha=0.6`, the cryptographic channel has more weight.
Verdict thresholds:
- `> 0.8` → `VERIFIED`
- `>= 0.4` → `UNVERIFIED`
- `< 0.4` → `BLOCKED`

It also returns a user-facing message describing the result.

5. SIGNER / HSM SIMULATOR ARCHITECTURE
--------------------------------------

Signer folder: `signer/`
Primary files:
- `signer/keygen.py`
- `signer/signer.py`
- `signer/verifier.py`
- `signer/keys/` directory for generated keys

### 5.1 `signer/keygen.py`

This script generates an ECDSA key pair on curve P-256 (`SECP256R1`).
It writes:
- `keys/private_key.pem`
- `keys/public_key.pem`

Key generation details:
- The private key may be encrypted if the environment variable `ZTDPP_KEY_PASSPHRASE` is set.
- If no passphrase is set, the private key is written unencrypted with a warning.

It also computes and prints a SHA-256 fingerprint of the public key.
It instructs the operator to register the public key with the backend using `/register-device`.

This is the provisioning step for the HSM-like signing flow.

### 5.2 `signer/signer.py`

This is the signing utility used by the backend `/sign` endpoint.
It performs the following sequence:
1. validate the input file extension (`.jpg`, `.jpeg`, `.png`)
2. open the image with Pillow and convert it to RGB
3. compute `pixel_bytes = image.tobytes()`
4. compute `sha256_hash = sha256(pixel_bytes)`
5. load the private key from `keys/private_key.pem`
6. sign `pixel_bytes` with ECDSA P-256 and SHA-256
7. base64-encode the signature
8. compute the public key fingerprint from the public key DER bytes
9. build a JSON manifest containing:
   - `ztdpp_version`
   - `device_id`
   - `timestamp`
   - `sha256_hash`
   - `signature`
   - `public_key_fp`
   - `image_width`
   - `image_height`
10. inject the manifest into the image:
    - JPEG: EXIF `UserComment` using `piexif`
    - PNG: `tEXt` chunk with key `ZTDPP_Manifest`
11. save the signed output as `<original>_signed.<ext>`

Important implementation details:
- For JPEG, it uses `piexif.insert()` to avoid re-encoding the JPEG image data. This preserves exact pixel bytes, which is critical because the signature is computed over the decoded pixel values.
- For PNG, it uses Pillow’s `PngInfo` text chunk insertion because PNG metadata is handled differently.
- The manifest is compact JSON with no whitespace to avoid metadata corruption.

The signer embeds the provenance manifest directly inside the image file so the verifier can extract it later.

### 5.3 `signer/verifier.py`

This standalone verification script mirrors the backend crypto verification logic.
It reads:
- the image file
- the embedded manifest from JPEG EXIF or PNG tEXt
- the public key from `keys/public_key.pem`

It computes:
- raw pixel SHA-256 hash
- ECDSA signature verification over the same pixel bytes

It prints a human-readable report with:
- hash integrity result
- signature verification result
- all manifest fields
- a final PASS/FAIL verdict

This script is useful for manual testing and debugging of the signing pipeline.

### 5.4 HSM Simulation

The frontend’s `SignerPage` sends the selected image and device ID to the backend `/sign` endpoint.
The backend does not sign directly in memory; it executes `signer/signer.py` as a subprocess.
This is the simulated HSM behavior:
- signing is isolated in a separate process
- the image is uploaded to the backend and then signed as if the camera sensor produced the provenance manifest
- the signed image is returned to the frontend as a download

In the backend, the signer subprocess is invoked with a Python interpreter at:
- `../venv/Scripts/python.exe`
This ensures the signing operation runs in the same virtual environment as the project.

The entire signing flow is thus:
1. frontend uploads image + `device_id` to `/sign`
2. backend saves the file temporarily
3. backend calls `signer/signer.py`
4. `signer/signer.py` signs the image and writes a signed file
5. backend returns the signed file to the browser
6. the browser downloads the signed file

6. LINKAGE BETWEEN FRONTEND, BACKEND, AND SIGNER
--------------------------------------------------

The full chain is:

frontend `App.jsx` → `api/api.js` → backend `main.py`

For verification:
- `App.jsx` calls `verifyImage(file)`
- `api.js` POSTs to `/verify`
- `backend/main.py` calls `crypto_verifier.verify(path)` and `ai_inferencer.predict(path)`
- `backend/aggregator.compute_trust(...)` computes the trust score
- the backend responds with `VerifyResponse`
- `App.jsx` renders the result with `TrustScorePanel`, `VerdictBadge`, and `BreakdownSection`

For signing:
- `App.jsx` renders `SignerPage`
- `SignerPage` calls `signImage(file, deviceId)`
- `api.js` POSTs to `/sign`
- `backend/main.py` saves the file and launches `signer/signer.py`
- `signer/signer.py` creates a signed image with embedded manifest
- backend returns the signed image as a file download

Device registration flow:
- `signer/keygen.py` prints instructions to use `/register-device`
- the backend’s `registry.py` stores the registered public key
- `backend/crypto_verifier.py` uses `get_public_key(device_id)` to validate signatures

8. HOW SIGNATURES AND PROVENANCE WORK IN ZTDPP
---------------------------------------------

The cryptographic provenance model uses this structure:
- The image pixel data is hashed with SHA-256.
- The pixel bytes are signed directly with ECDSA P-256.
- The signed data is stored in the image metadata manifest.
- The manifest also stores the `device_id` and `public_key_fp`.
- The backend verifies both the hash and the signature.
- The public key is trusted only if the device is registered in the backend registry.

This means ZTDPP combines:
- deterministic proof of origin (cryptographic provenance)
- probabilistic authenticity assessment (AI deepfake detection)

And it fuses them using the weighted trust formula.

11. IMPORTANT BEHAVIORAL DETAILS
-------------------------------

- The signer signs raw pixel bytes after converting every image to RGB. This makes the signature deterministic across input color modes.
- JPEG signing preserves bit-exact image data by injecting EXIF rather than re-saving the image.
- PNG signing uses metadata text chunks because PNG does not use EXIF in the same way.
- The backend AI module clamps outputs to avoid overconfident predictions.
- The final trust score will never be fully trusted unless cryptographic verification passes, because a failed signature forces `crypto_score=0`.
- The frontend prevents uploading unsupported files and restricts size to 10 MB.
